# Keyhole PWA (Installable Shell) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Make Keyhole installable to a phone or desktop home screen, and make the app itself load with no network — while keeping the vault exactly as network-dependent as it is today.

**Architecture:** A web app manifest plus a hand-written service worker that precaches the built **shell** (the hashed JS/CSS and `index.html`) and nothing else. The vault is never cached to disk. This is a deliberate narrowing of spec §6.5's "offline read against the encrypted cache": the memory-only session is this product's device-theft defense, and writing vault ciphertext to disk — even encrypted — would let a stolen device yield the encrypted vault and the plaintext collection names. So the app *loads* offline and shows the unlock screen; the vault still requires a connection to populate, and the UI says so plainly rather than showing an empty or broken vault.

**Tech Stack:** Vite 6 build, a hand-written service worker (no PWA framework), the Go `embed.FS` server that already serves the built app.

## The rule this entire plan turns on

**The service worker must NEVER cache a response to `/api/*`.** Those responses carry bearer tokens and vault ciphertext. A naive "cache everything" service worker would write the vault to disk — which is the exact outcome the shell-only scope exists to prevent. Every task is subordinate to this rule, and it has its own test: fetch an `/api/*` path through the SW, then assert the SW cache does not contain it.

## Global Constraints

- **No vault data reaches disk.** Not IndexedDB, not the Cache API, not `localStorage`. The Cache API holds static shell assets only. `localStorage` still holds at most `keyhole.email` and `keyhole.autolock`. The e2e storage assertion — `indexedDB.databases()` empty — must stay TRUE and becomes a guard that no vault cache was added.
- **The service worker is registered only in the production build.** Not in dev (it fights HMR), not in tests. A dev or test run must behave exactly as it does today.
- **Same-origin only**, consistent with the server's CSP `default-src 'self'`. The SW fetches nothing cross-origin.
- **The SW must not trap a user on a stale build.** Hashed asset filenames are cache-first (immutable); `index.html` is network-first with a cache fallback, so a new deploy is picked up on the next load while still working offline.
- **No new runtime dependency without reporting first.** Prefer a hand-written SW with a precache list generated by a small Vite hook over a PWA framework. If generating the hashed-filename precache list genuinely needs a dependency, stop and report before adding one.
- Test names describe what the body verifies. Every task ends with a mutation check.

## Task 2: The service worker

**Files:** Create `apps/web/src/sw.ts` (or `public/sw.js` + a build step), a Vite hook to emit it with a precache list, and its test.

This is the security-critical task. Build it so its logic is unit-testable without a browser — a pure function that decides, per request, `precache-first | network-first | bypass`, tested directly, plus the thin SW glue that calls it.

**The routing rules:**
- **`/api/*` → BYPASS.** Never cached, never served from cache, straight to the network. This is THE rule.
- **A hashed asset** (`/assets/*` with a content hash in the name) → **cache-first**, immutable, from the precache.
- **`index.html` / the navigation request** → **network-first**, falling back to the cached shell when offline. This is what makes a cold offline load reach the unlock screen instead of a white page, while still picking up a new deploy when online.
- **Anything else same-origin not in the precache** → network, no caching.

**The lifecycle:**
- `install`: precache exactly the current build's shell assets (the generated list), then `skipWaiting()`.
- `activate`: delete every cache whose name is not the current build's, then `clients.claim()`. This is what stops a stale build from persisting — a new SW version wipes the old precache.
- The cache name embeds the build hash, so activation is a clean swap.

**The precache list** is the set of hashed filenames Vite emitted plus `index.html`. Generate it at build time (a Vite `generateBundle`/`writeBundle` hook that writes the list into the SW, or a virtual module the SW imports). Do not hand-maintain it — a hand-maintained list goes stale on the first build and precaches a file that 404s, which fails `install`.

**Tests (on the pure routing function, no browser needed):**
- an `/api/sync` request routes to BYPASS
- an `/api/auth/login` request routes to BYPASS (auth, not just data — both carry secrets)
- a `/assets/index-AbC123.js` request routes to cache-first
- a navigation request (`/`, `/enroll/x`) routes to network-first
- **after handling an `/api/*` request, the cache contains no `/api` entry** — the rule, tested through a fake Cache
- the precache list contains `index.html` and at least one hashed asset (proves the build hook ran)

**Mutation — mandatory, and it is the important one:** change the `/api/*` rule from BYPASS to cache-first. The "no `/api` entry in the cache" test must fail. Capture verbatim output, revert. If it does not fail, the test is not actually inspecting the cache and must be fixed — this project has produced ten prescribed mutations that did not fail, and this is the one that must not.

## Task 3: Register it, and be honest about offline

**Files:** Modify `apps/web/src/main.tsx` (registration), and the boot/unlock path in `src/ui/`.

- Register the SW **only in the production build** — guard on `import.meta.env.PROD`, and check `"serviceWorker" in navigator`. A failed registration is logged and swallowed; the app must work without it.
- **On a new SW version, do not silently reload under the user's hands.** The `activate`/`skipWaiting` from Task 2 swaps assets on the next navigation; that is enough. Do not add an auto-reload that could interrupt someone mid-edit.
- **Offline honesty.** The app already distinguishes `NetworkError` from a server error (design spec §9). When the user is offline and the vault cannot sync, say so specifically — "You're offline. Connect to load your vault." — distinct from "the server had a problem." A cold offline load must reach the **unlock screen**, not a white page and not a fake empty vault. If `navigator.onLine` is false at boot, the unlock screen can say the connection is needed before it is even attempted.

**Tests:**
- registration is not attempted in a non-prod environment (assert `navigator.serviceWorker.register` is not called when `import.meta.env.PROD` is false)
- an offline unlock attempt shows the offline message, not a wrong-password or generic-server message (mock a `NetworkError` at boot / first sync)

**Mutation:** make the offline path show the generic server-error message. The offline-message test must fail. Revert, capture.

- [ ] TDD; run the mutation; commit: `feat(web): register the service worker in production and say when you're offline`

## Task 4: End to end — installable, loads offline, leaks nothing

**Files:** Create/extend `apps/web/e2e/` — a PWA journey. Playwright drives a real Chromium with service-worker support.

- **Installable:** the built app serves a valid manifest and registers a SW; assert the SW reaches `activated`.
- **Loads offline:** unlock online, then go offline (`context.setOffline(true)` / route abort) and **reload** — the app shell still loads and reaches the unlock screen rather than a browser error page. (It will not show the vault offline — that is the design; assert the honest offline message, not a populated vault.)
- **THE leak assertion:** after using the app and going offline, inspect what is on disk. `indexedDB.databases()` is empty. The SW Cache API contains **only** shell assets — enumerate the cache and assert no entry's URL starts with `/api`, and that no cached response body contains a known plaintext password that was in the vault. This is the test that proves the shell-only decision actually held.

Known footguns, already paid for: `--host 127.0.0.1`; `reuseExistingServer` off in CI; shared DB → `test.describe.serial`. **A service worker needs the app served as a build, not the dev server** — serve the production build (or the Go binary serving the embedded dist) for this spec, since the SW is prod-only. Say how you served it.

## Self-review

Spec §6.5 (manifest, service worker, home-screen install, offline) → Tasks 1–4, narrowed to shell-only and recorded in Task 5. §3.9.2 (web-app code delivery) is unchanged: a service worker persists cached JS, but `index.html` stays network-first so a new deploy is picked up, and a compromised server can still serve new JS on the next visit — the SW neither worsens nor fixes that limitation, and Task 5 says so.

**Deliberately not built:** the on-disk encrypted vault cache and offline cold-unlock. Both are real features, both weaken the device-theft posture, and both were declined in favour of keeping "steal the device, get nothing" true. They remain available as a future opt-in.

**The risk this plan carries** is a single rule with a silent failure mode: a service worker that caches `/api/*` writes the vault to disk and defeats the whole decision. Task 2's mutation exists precisely to prove that rule's test can fail, and Task 4's leak assertion proves it against a real browser.
